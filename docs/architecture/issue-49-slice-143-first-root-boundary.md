# Suite #49 — Slice 143: externally pinned first-root review boundary

**Expected parent:** `7d77bde891d454221b93338557595dbbca50a7da`.

## What is implemented

This is a production-code **read-only enrollment candidate gate**, not a
production enrollment or installation. It reuses the existing Ed25519 and
strict digest-pinned trust-policy implementations rather than creating another
cryptographic signing format. `review_first_root_quillan_candidate` requires an
`ExternalRootApproval` whose contents must be obtained **independently of the
untrusted candidate**. An approved policy must match the exact SHA-256 pin,
root key IDs and quorum, and minimum revision. A root-signed, current registry
must authorize exactly the independently approved Quillan publisher key IDs,
repository `Paper-Data-Suite/pds-quillan`, and distribution `quillan`.

The separately signed Quillan module claims must then pass the delegated
Ed25519 verification using that same approved keyring and registry. Registry
and module rollback/equivocation checkpoints are accepted as separately
controlled inputs; neither this function nor any caller-created object
provides durable rollback protection. Valid future signed module *versions*
can pass these claim checks without matching the historical Suite version.
That is metadata-only: no wheel bytes, transitive dependencies, executable
launcher, protected active receipt, or installed machine is inspected here.

## First-root bootstrap is NOT self-authenticating

A candidate policy, downloaded JSON, publisher release asset, GitHub page, or
operator-entered SHA-256 from the same source may **not** supply its own pin.
The Python `ExternalRootApproval` class is an input contract, *not* an
unforgeable security capability. Any Python caller can construct it. The
function cannot prove who reviewed or protected those values. Accordingly its
result always reports `independent_approval_custody_verified=false`,
`publisher_identity_officially_attested=false`, and all enrollment, install,
and launch authority flags **false**. Nothing writes to ProgramData, SCM,
receipts, the classroom workspace, Git configuration, or a trust cache.

To actually establish production trust, an independently authorized publisher
must select and authenticate the root public keys and governance, a separate
administrator/installer must obtain that approval through a protected channel,
and a reviewed OS-protected root-policy store must enforce its continuity and
revocation/rotation rules. The administrator cannot simply sign the candidate
with a key generated by the same enrollment program and call that independent.
No production signing key, public key or digest is invented or distributed in
this slice. An independent root/signing ceremony remains a blocking external
precondition; the resulting protected approval must then be integrated into
an installed-service and receipt transaction.

## Acceptance and non-authorizing scope

The focused tests use **synthetic fixture keys** from the existing Issue #49
cryptographic tests to exercise actual signatures and rejection of wrong pins,
root quorums, unauthorized Quillan delegation, cross-module key use,
unsigned or expired metadata, and checkpoint rollback. A signed future-version
claim is accepted for review without an upgraded Suite wheel. It is never
reported as an authenticated installed wheel, approved update, or permitted
launch. No CI host account, private key or system setting is changed.

## Next unblocker

An independent root custodian/publisher and an independent administrator must
establish the authentic PDS production root key, its out-of-band SHA-256 and
protected custody. Only after that external act should an installer enrollment
writer and launch eligibility consumer be enabled, with negative acceptance
against actual ordinary teacher accounts and signed official wheel bytes.
