# Issue #49 — Slice 87: protected capsule deletion dispatch

## Boundary

Following Slice 86's immutable `CAPSULE_PREDELETE_UNCERTAINTY_ARMED_NO_DELETE_DISPATCH` state, Slice 87 introduces a **separate one-shot, service-owned deletion dispatch claim**. Its durable row `plan_capsule_delete_dispatch_v1` retains the exact installation, transaction, request, successor, generation/revision, predelete marker, clearance preflight, original capsule digest, service-pinned capsule identity, active receipt target identity and independent writer-fence digest. The sole status is `CAPSULE_DELETE_DISPATCH_CLAIMED_OUTCOME_UNCERTAIN`, with explicit no-retry/no-launch authority.

The protected claim is inserted **and committed on the exact Slices 78–86 SQLite connection before any external filesystem deletion is invoked**. The next external call can therefore run *at most once from the coordinator*. Loss of a database acknowledgment, process crash, deletion callback failure, unchanged capsule or post-delete readback failure must never cause automatic re-dispatch; a protected operator must independently reconcile the actual filesystem state. An absent capsule is not evidence that the commit is safe to repeat. The SQLite transaction does not atomically cover an operating-system unlink.

## Preconditions and ordering

1. Canonically revalidate the original request and protected reservation, receipt, deployment intent, local prewrite, receipt dispatch, convergence, clearance preflight and capsule predelete marker. Compare actual rows re-fetched under `BEGIN IMMEDIATE`, with the one-shot claim row still absent. Caller-provided records never function as bearer capabilities.
2. Require the separately authenticated `dispatch_capsule_delete_once` service operation, fresh signed successor witness head under the independently pinned key, exact original capsule bytes under the independently protected capsule file identity, and two stable independent capsule, receipt and no-inflight writer-fence samples. Any changed capsule, target, witness, writer or data basis refuses **before** a deletion claim.
3. Commit the exact one-shot deletion claim to protected SQLite. Once claim commit is attempted, any uncertain outcome requires *read-only operator reconciliation*, not another `dispatch_once` or automatic rollback.
4. Only after the successful protected COMMIT, invoke the separately provisioned `IndependentCapsuleFileDeleter` with the signed request and **protected pinned capsule identity**, never an untrusted local filename. The external service must independently enforce same-file handle verification, exclusive OS locking, reparse and hard-link protections, access-control separation, exclusive capsule parent custody, durability and no unrelated file deletion.
5. Independently sample the post-delete state using a **different** reader whose schema permits absence. Require the exact installed successor, unchanged selection, proposal and journal, no capsule bytes, independent absence confirmation, terminated deletion operations, exclusive fences, directory durability check, and renewed signed witness successor. A success response remains `CAPSULE_ABSENT_POSTDELETE_RECONCILIATION_REQUIRED` and carries no launch authority. Post-commit evidence is diagnostic only; no new protected outcome claim is appended in this slice.

## Refusal and follow-on

Neither this coordinator nor its tests establish privileged Windows filesystem behavior. The Python callbacks are **not authentic** merely because they match a protocol or dataclass. Real production deployment requires an independently administered service, protected configuration/key/clock, real ACL/reparse/handle checks, durable SQLite and filesystem behavior, process-wide writer quiescence and Windows crash/power-loss fault injection. A callback that lies, races, or loses its ACK cannot be made trustworthy by these structural tests.

No launcher readiness, slot switch, rollback, recovery authority, another witness CAS, or local receipt write is granted. The untrusted teaching workspace must never be able to construct an independently privileged deleter. **Slice 88** must offer independent, read-only post-delete crash reconciliation and a distinct durable completion certificate only after verified absence and continued protected successor custody; further launcher readiness is a different gate.
