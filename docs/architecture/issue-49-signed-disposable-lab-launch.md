# Issue #49 — Slice 101: Signed release to disposable installed launch acceptance

This slice adds **one explicit, non-production, Windows Quillan 0.10.6 acceptance route**. It moves beyond the historical-version refusal reproduction: the implementation authenticates the existing root/delegated signatures and exact Quillan wheel, compares all signed wheel members with installed bytes in the isolated full-dependency laboratory, resolves **the runtime dependency metadata closure (including selected extras)** within that laboratory, checks console-script ownership and examines its generated Windows launcher wrapper. When and only when the teacher invokes `--execute-help`, it runs the lab's `quillan.exe --help` and checks exit status.

The command is `python -m paper_data_suite.evergreen_signed_lab_launch`; it does **not** replace `pds launch` and is not installed as a new global entry point. It requires an exact lab folder name `historical_suite_010_quillan_0106_FULL_DEPS_LAB`, a separate virtual environment, and the authenticated source wheel and envelope files produced by the Slice 100 local issuance ceremony. It does not read, write, install, import or launch against the teacher's live application workspace. Default operation is inspection only; even the opt-in path permits only `--help` and no additional arguments.

Trust limitations are deliberate. The `--trust-sha256` value must be independently retained and checked by the teacher, not taken from a downloaded trust-policy file. Local key ownership from a development ceremony is **not official PDS publisher authorization**. Revision anti-rollback is not protected here. Runtime dependency closure checks versions and declared requirements but **does not authenticate transitive wheel origins or byte content**. The Windows interpreter and launcher executable's *native code* remain **unauthenticated**, despite their wrapper metadata matching. A time-of-check/time-of-use gap remains between inspection and the opted-in subprocess. No OS-isolated service, independent installed-receipt head, code-signing chain, exclusive launch fence, or production deployment authority is provisioned. The returned observation explicitly records `native_executable_authenticated=false`, and has no launch-token attribute.

Acceptance of the local synthetic test fixtures or the user's signed lab is a step toward a verified version-flexible launcher; it must not be used to bypass the historical `pds launch` gate in an active classroom installation. Production activation requires independently provisioned publisher roots and protected installation/witness records, plus authenticating all execution and dependency bytes before dispatch.
