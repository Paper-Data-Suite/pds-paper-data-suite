# Suite #49 — Slice 141: ephemeral RSA-PSS detached-signature test

**Parent:** `362926dbda4ce41793bbb8267693a8e2bb355e05`.

## Purpose

Build a narrowly scoped cryptographic experiment on the already qualified,
**ephemeral**, OS-anchored Windows CI sandbox. Slice 140 demonstrated Windows
filesystem ACL denials for a synthetic payload. This slice tests how a separately
invoked verifier can bind the exact synthetic payload bytes to a detached
RSA-3072 / RSA-PSS / SHA-256 signature and require tampering to fail closed.

A CI-only elevated signer creates a fresh private/public key pair *in memory*,
then writes only the SPKI-encoded public key and detached signature under the
sandbox's administrator-restricted `protected-state/service-state` directory.
The private key is never exported to disk. It uses a fixed domain prefix
`PDS_SUITE49_EPHEMERAL_TEST_SIGNATURE_V1` and fixed synthetic payload bytes;
no file path, package, private key, URL or publisher thumbprint is user-supplied.

A separate, fresh PowerShell verifier process reads the already-staged payload,
public key and signature. The verifier requires that the correct signature
validates. It additionally refuses verification for (1) one modified payload
byte, (2) one modified signature byte, and (3) a substituted unrelated RSA-3072
public key. This checks a positive cryptographic control and three negative
controls. The parent process independently re-reads the protected test files'
bytes, ACLs and the original payload hash after verification.

## Security boundary

This is **not PDS publisher authentication** and not an Authenticode signing
flow. Crucially, the signing key was generated by the same disposable CI test:
it is **not** a previously approved, externally pinned production trust root.
An attacker who can replace both the signed payload and its trust anchor could
produce matching new test-only signatures. Thus a successful cryptographic
verification alone is not evidence of independent release provenance.

The signer and verifier refuse outside GitHub-hosted Windows CI, refuse without
an elevated administrator token, and require an exact GUID-named sandbox below
the OS-resolved CommonApplicationData directory. The signer additionally
requires the explicit `EPHEMERAL_RSA_PSS_TEST_ONLY` acknowledgement. All writes
are confined to two new files below the throwaway protected sandbox; no service,
real Paper Data Suite installation, receipts, publisher pin or classroom data
are touched. The regular source ZIP runner only runs lint, source tests, commit
and push; it does **not** execute the signing or verification scripts locally.
No cleanup, deletion, rollback or production installation is performed.

The CI step reports
`SLICE141_EPHEMERAL_RSA_PSS_VALID_AND_TAMPERS_REJECTED` only after all
cryptographic controls and post-test readbacks pass. It continues to declare
`independent_publisher_provenance_verified=false`,
`trusted_release_artifact_verified=false`,
`production_rollback_protection_verified=false` and
`authorized_to_install=false`. The same result must **never** authorize a
production write, deployment, receipt, service or activation.

## Remaining implementation work

A real installer still requires an independently provisioned and authenticated
publisher trust anchor, properly signed release artifacts and dependency lock,
secure OS-held staging, rollback-resistant checkpoint journal, a documented
administrator privilege boundary, and actual installed-service acceptance under
a separately authenticated nonadministrator account. This test establishes none
of those permissions; it only exercises detached-signature verification against
one synthetic artifact on a disposable CI machine.

No production deployment is performed or authorized in this experiment.
