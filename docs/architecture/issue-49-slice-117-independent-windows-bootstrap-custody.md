# Issue #49 — Slice 117: independent Windows bootstrap custody and checkpoint CAS

**Classification:** architecture/contract and pure proposed transition, **NOT** an installer or administrative authorization. Parent: Slice 116 (`7e089dcf0f7dd26932177a498ade6bfa97afbad8`).

## Motivation and precise scope

Slices 112–116 verify a **teacher-constructible request** against increasingly strong signed artifact, dependency-lock and revision metadata. Slice 116's `InstallerTrustCheckpointReview` is still created in a user-controllable Python process. Neither its `expected_policy_sha256` argument nor its `previous_registry` / `previous_lock` arguments independently proves key custody or rollback protection. Therefore none of these reviews may authorize a Windows installation, service, protected receipt or activation.

Slice 117 introduces **one testable, pure checkpoint compare-and-swap proposal** (`evergreen_windows_installer_checkpoint_cas.py`), not another diagnostic-only CLI. It also specifies how a future independently deployed native Windows installer/service must establish each necessary control before it may consume that proposal. It does not create an installer executable, elevate, launch PowerShell, change ACLs, register a service, write a checkpoint, or touch classroom data.

## Independently privileged architecture (required future implementation)

1. **Installer acquisition and identity.** A separately distributed code-signed native installer (not imported from the teacher-writable Python suite) must be launched by an authenticated administrator through Windows' own privilege elevation/consent. It must establish the **effective** elevated process token and integrity level with OS APIs, not infer privileges from a username, environment variable, service name, Python review field, or untrusted request. Distinguish a UAC credential prompt from informed, explicit consent for this exact new-install transaction and signed wheel inventory. An expired/changed consent, mismatch or absent administrator is refusal. No unattended or implicit install from a normal teacher command.
2. **Pinned root of trust.** The initial Ed25519 policy hash/root set must ship in a separately authenticated installer image or a previously protected OS-managed enrollment; **never** read a root hash from the request, downloaded catalog, teacher config, or a mutable package path. Existing `load_digest_pinned_trust_policy` and the signed registry/dependency-lock verifiers can perform parsing and signature checking only **after** this independent bootstrap. Root rotation requires an independently authenticated threshold/transition protocol and durable update; Slice 117 intentionally refuses root-policy changes.
3. **OS-anchored protected paths.** Resolve Program Files and ProgramData through Windows Known Folder/OS APIs (not `%ProgramData%`, shell path strings or caller-provided directories). Open directories by handles, reject reparse/junction/symlink substitutions, inspect final paths, owners and effective DACLs. Provision only through the authenticated installer with SYSTEM/administrators and a specifically configured service identity retaining required access; ordinary teachers must lack write, delete, ownership and DACL-change authority over binaries, checkpoint/transaction records, active receipts and the SCM service object. Recheck after provisioning and before committing.
4. **Service custody and lifecycle.** Register `PaperDataSuiteService` through the SCM only under independent installer identity. Protect the service object DACL from ordinary-user configuration, deletion and control; select and verify service account, SID type, effective privileges and token at runtime, independently of local JSON. Verify the executable bytes, signature/provenance, DACL and parent-directory custody after installation. Do not let an arbitrary locally supplied module execute as a privileged service component.
5. **Initial protected genesis state.** Only the independently authenticated installer can create the **generation-zero** canonical checkpoint after it has provisioned and verified protected storage. That state contains an immutable policy revision/digest and zeroed registry/lock/transaction fields. A teacher-generated byte string with the same shape is **not** a real genesis credential. A missing protected record on an already provisioned machine is a security/recovery failure, not an opportunity for user-side reinitialization. Bind the genesis to the installation identity and a separately protected service-state root in the native record/ledger; the pure JSON in this slice does not supply such identity.
6. **Signed wheel/recovery checks.** Reverify Slice 116's registry/lock/wheelhouse inputs in the privileged process using the independent root and **actual protected previous** checkpoints. Authenticate the recovery basis independently; `InstallerIntent.recovery_basis_sha256` is an unauthenticated claim and Slice 117 intentionally does **not** copy it into protected checkpoint state. Enforce closed, exact-hash wheelhouse and no uncontrolled pip/network sources. Refuse any mismatch or rollback.
7. **Serialized protected checkpoint transaction.** Hold a service-owned exclusive transaction/ledger lock. Under that lock, read a protected, validated previous record and independently compare its digest and generation against `CheckpointCasProposal.expected_previous_sha256` and `.expected_generation`. Revalidate the signed evidence and current service/ACL custody; generate the deterministic next record, verify the proposal's bytes/digest, and write an *intent journal* before a native atomic replacement. Flush data and parent metadata as supported by the underlying Windows filesystem, use a durable replace/rename procedure with reparse-safe handles, and journal the committed generation. On interruption, restart must compare the journal, prior and next hashes, the signed install evidence, and live installed state to resolve or **stop closed**. Never publish the active receipt or launch until independent post-install proofs and recovery commit succeed.
8. **Rollback protection.** A normal NTFS DACL prevents ordinary users from writing state but does **not** prevent an administrator or offline disk restoration from rolling back the entire protected ledger. Production antirollback therefore also requires a separate independently controlled high-water mark/witness (for example suitable TPM-backed or enterprise-managed monotonic storage) whose durability, availability and authorization model is validated. A local signed-cache file, this JSON record, and a SHA-256 chain alone are insufficient. If independent continuity cannot be proved, installation/activation must fail closed.
9. **Negative acceptance.** Test with an ordinary teacher token that binaries, signer pins, recovery journal, checkpoint ledger, receipt head, directory DACLs, service configuration and SCM security cannot be modified. Probe junction/reparse swaps, hardlink attacks, concurrent transactions, old policy signatures, equal-revision equivocation, stale checkpoints, replay, staged artifacts changed after verification, process crashes before/after checkpoint replacement, and tampered receipts. A passed Python regression cannot substitute for Windows native negative acceptance.
10. **Activation separation.** The independently validated protected service must separately gate active receipt publication and launch only after all seven Slice-111 administrator phases, witness/CAS continuity, native file inventory, service token, and negative acceptance tests pass. No bootstrap transition proposal is an activation token.

## Pure Slice 117 checkpoint format

`parse_claimed_checkpoint(raw)` enforces strict canonical, UTF-8, duplicate-key-free JSON (max 4,096 bytes). Fields: `schema=1`, `generation`, `trust_policy_sha256`, `trust_policy_revision`, `registry_revision`, `registry_sha256`, `lock_revision`, `lock_sha256`, `last_transaction_id`, `last_request_sha256`. Lowercase 64-hex hashes and 32-hex transaction IDs are mandatory. A genesis record (`generation=0`) must have a nonzero pre-pinned trust policy, zero registry/lock revisions+hashes, and zero last transaction/request. A progressed record requires nonzero signed revision/hash and transaction/request. Unknown fields—including any approval assertion—are rejected.

`propose_installer_checkpoint_cas(raw_intent, review, claimed_previous_bytes)` parses the Slice-112 canonical request, compares it to the non-authorizing Slice-116 review, refuses `True` authority flags, checks policy identity, rejects registry/lock rollback or same-revision digest equivocation, rejects transaction replay, and requires **generation zero** for the `NEW_PROTECTED_WINDOWS_INSTALLATION` operation. It returns a deterministic candidate generation-one JSON record plus prior SHA-256/generation CAS expectations. **No I/O occurs.** Untrusted bytes or fake reviews may still yield a syntactically sound proposal; only the native trusted custodian can decide whether the old state and signed evidence are genuine and effect the write.

The proposal's `protected_baseline_authenticated`, `atomic_write_performed`, `service_or_admin_authenticated`, `authorized_to_provision`, `authorized_to_register_service`, `authorized_to_publish_receipt`, and `authorized_to_activate_or_launch` are always `False`. Its status is `PROPOSED_PROTECTED_CHECKPOINT_CAS_NOT_APPLIED` and its authority is `NO_INSTALLER_APPROVAL_PROVISIONING_SERVICE_RECEIPT_OR_LAUNCH_AUTHORITY`.

## Qualification and explicit non-goals

Unit tests cover deterministic encoding/CAS hashes, immutable policy, missing/extra canonical fields, malformed/duplicate JSON, zeroed genesis, invalid revisions/digests, replay, equal-revision equivocation, a new-install request against existing state, review forgery and absence of a mutation API. The guarded runner also executes the earlier Windows custody, signature, signed-wheel, closed-wheelhouse and trust-checkpoint tests. Test cases with large byte strings use bounded explicit parameter IDs to avoid the Windows pytest environment-variable limit.

**Not implemented:** real native installer, code signing or production root keys; administrator/UAC authentication; OS-native handle/DACL/SCM enforcement; protected genesis enrollment; durable CAS/journaling/TPM witness; classroom installation; receipt or activation. Future work must be built and tested independently before claiming these features are deployed.

## Suggested next native implementation checkpoints

A. Build/authenticate a minimal native Windows installer with embedded independently pinned public trust roots, an explicit administrator consent UI, and fail-closed token verification. B. Implement and negative-test handle-based protected state creation and a durable locked checkpoint ledger, including crash/recovery and independent antirollback witness. C. Establish SCM service identity/configuration/executable custody with ordinary-user negative tests. D. Integrate Slices 114–117 in the native transaction, then add an independently controlled receipt/activation release gate. Each item requires OS-level acceptance evidence, not just Python unit tests.
