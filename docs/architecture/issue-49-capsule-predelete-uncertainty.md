# Issue #49 — Slice 86: protected capsule pre-delete uncertainty (no deletion)

## Decision and scope

The Slice 85 preflight `CAPSULE_CLEARANCE_PREFLIGHT_RECORDED_NO_DELETE_DISPATCH` is **not** permission to delete a recovery capsule. Slice 86 adds a distinct, append-once uncertainty barrier on the **same independently administered SQLite connection** as Slices 78–85. It records that an external deletion *might be considered by a later, separately authorized service*, but does not dispatch a deletion, open a file for writing, clear the capsule, switch code, roll back, invoke witness CAS, or launch software. The only new durable status is `CAPSULE_PREDELETE_UNCERTAINTY_ARMED_NO_DELETE_DISPATCH` with a negative authority string. The marker is diagnostic, never a bearer permission token.

## Exact canonical and durable basis

The `ProtectedCapsulePredeleteUncertaintyLedger` requires the actual `ProtectedCapsuleClearancePreflightLedger` and its exact SQLite connection, which is shared with the earlier protected finalization, preclaim, protected receipt, local deployment, prewrite, dispatch and convergence tables. It authenticates distinct service operations `arm_capsule_predelete_once` and `observe_capsule_predelete`, plus all earlier authorized reads. Every request must be canonical and agree with the typed original Slice 78–84 inputs. The supplied Slice 85 preflight must have its exact status and non-authorizing authority, match the original transaction/request/successor/generation/revision, equal the full protected Slice 84 convergence-record hash, and bind the same reserved recovery capsule, target and fenced-evidence digests. The independently pinned capsule identity must equal the original preflight's identity.

Inside a single `BEGIN IMMEDIATE` SQLite transaction, the service re-reads the *actual durable* Slice 78–85 records and refuses missing/changed records. It rejects any prior Slice 86 row, even if identical. This prevents a caller from substituting forged dataclasses or reopening a one-shot deletion attempt by replay. It does **not** make a separate filesystem delete transactional with SQLite.

## Fresh protected physical evidence before arming

Before recording, the service requires a fresh independently administered capsule reader returning the **actual bounded capsule bytes** (not just a caller-chosen digest). The two samples must be identical, match the original reserved `recovery_capsule_sha256`, and report the pinned capsule identity, protected regular file, protected directory, and exclusive capsule fence with no new capsule writers. Across both samples it must also verify independent installed bytes, original service approval, exactly visible successor local receipt, prior filesystem-writer termination, exclusive OS fence, no unaccounted in-flight writer, and the same fence/termination digest that was recorded in the prior convergence and clearance preflight. A new challenge-bound signed successor witness readback occurs between the two sets of samples, under a separately pinned witness key and current trusted clock.

The new row binds the complete Slice 85 preflight (all dataclass fields, including its negative authority) by canonical SHA-256, the complete Slice 84 convergence record hash, original request and signed successor, capsule digest, pinned capsule identity, configured local target and independently fenced-evidence hash. A single SQLite `COMMIT` records exactly one marker for an installation. After a lost ACK, an uncertain commit, or an absent marker following a crash, **never automatically retry, rearm, delete, or roll back**. Only read-only observation and supervised reconciliation may follow; no `reset`, `UPDATE`, or `DELETE` operation is provided.

## Production limitations and next boundary

An immutable Python dataclass, SQLite transaction, synthetic witness, or test callback does not prove Windows service privilege separation, protected filesystem ACLs, safe volume/file identity, reparse-point resistance, process-wide locks, durability, physical consent freshness, or independent clock custody. Real deployment requires those guarantees and Windows crash/fault injection tests. No backend delete API is implemented or invoked in this slice. A future **one-shot protected deletion dispatcher** must preserve a durable uncertainty marker before any file mutation, avoid automatic retry after an ambiguous outcome, and independently classify post-delete physical state. Even successful capsule deletion must remain separate from launcher readiness and human-authorized activation.
