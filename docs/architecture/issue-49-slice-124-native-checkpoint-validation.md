# Issue #49 — Slice 124: native checkpoint/journal content validation

**Parent:** `0986ff87eec01bd9d37c68a2cbfc47b79ccf66c8` (Slice 123). **Scope:** native x64 and native ARM64 read-only validation of the *contents* of a held-handle checkpoint/journal pair, plus a portable C++17 negative-test executable. This is **no service**, **no receipt**, no provisioner, no signed installer, and no protected writer.

## Security boundary advanced

The native diagnostic previously held five Win32 handles, checked owner and DACL, and read up to 4,096 bytes from each record, but only tested successful I/O. Slice 124 requires the bytes to parse according to the exact canonical Slice 117/118 checkpoint/journal schemas before reporting an observation. A separate Windows CNG SHA-256 (`BCryptOpenAlgorithmProvider`, `BCryptHash`) computes the checkpoint digest from bytes actually read through those held handles. The native parser accepts only the three recognized new-install interruption relationships: prepared/previous, prepared/replaced, and replaced-claimed/replaced. All other combinations refuse. The diagnostic still returns `NATIVE_WINDOWS_CHECKPOINT_CUSTODY_NOT_ESTABLISHED` for absent or malformed states. A valid relationship is explicitly **not** a committed installation or license to resume.

The parser is a bounded fixed-schema C++17 contract rather than a permissive general-purpose JSON reader. It expects sorted compact JSON fields, required exact names/order, lowercase SHA-256 and transaction IDs, numeric values without signs/leading zeros/decimals/exponents, and a maximum of 4,096 bytes for either record. Duplicate, unknown, escaped, missing or reordered fields, malicious Unicode, booleans, extra whitespace, and inconsistent transaction records fail closed. The new-install contract requires generation 0 or 1; future upgrade/checkpoint generations require their own separately reviewed contract instead of being interpreted loosely.

## Native executable qualification

The separate `pds_checkpoint_contract_test` C++17 target exercises accepted interruption relationships and dozens of malformed-input refusals. It runs on **native x64** and **native ARM64** as part of the existing build-gate script; cross-compiled ARM64 only proves compilation, not execution. Its expected single success marker is `SLICE124_NATIVE_CHECKPOINT_CONTRACT_TESTS_PASSED`. The PowerShell gate checks its exit code and marker; subsequent normal diagnostic/unsupported-`--apply` checks retain their previous behavior, and script success still requires explicit `exit 0`. Compilation on Linux with g++ verifies portability of the parser, but cannot establish the Win32 CNG link or Windows runtime behavior.

## Limits and remaining Issue #49 requirements

Observed bytes, journal markers, and native read-only ACL inspection are not independently protected custody. Opening paths by name even while keeping ancestor handles is not a substitute for object-manager-relative secure file handles and locked service transactions. `BCryptHash` authenticates **byte identity only**; it does not authenticate the wheel publisher, installer image, administrator token, or OS protected high-water mark. Independent antirollback, Authenticode publisher pinning, administrator and SCM authorization, durable write-ahead logging and atomic CAS, interruption recovery, receipts and installed software verification all remain unimplemented. Ordinary teacher-token production-shaped negative tests and end-to-end official-wheel qualification remain separate acceptance gates. No classroom data is read or modified.
