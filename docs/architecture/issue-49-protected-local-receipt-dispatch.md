# Issue #49 — Slice 83: protected once-only local receipt dispatch

## Decision and authority boundary

Slices 78–82 created, in one independently administered SQLite service connection, a reserved finalization, one-shot publication preclaim, canonical protected successor receipt, exact local deployment intent, and a `LOCAL_PREWRITE_UNCERTAINTY_ARMED_NO_WRITER_DISPATCH` uncertainty marker. They did not write an active-receipt file. Slice 83 adds the **service-owned dispatch coordinator** and an injectable **privileged filesystem writer protocol**. This is the first step capable of *invoking* a write to the local receipt, but the Python library does **not** implement OS-level privilege isolation or a universal atomic-replace mechanism. Production must supply and authenticate those capabilities independently. There is no teacher CLI or writable HTTP endpoint.

A real deployment can use this coordinator **only** from an independently administered service with protected configuration, protected SQLite database and exclusive installation-writer fencing. `service_owned_write` MUST be service-provisioned, never built or selected by classroom-local code. Its callback signature is not evidence of privilege. No caller-controlled active-receipt path is accepted. The service must pin the destination identity and verify safe parent/file handles (including symlink/reparse and TOCTOU defenses), retain predecessor bytes, stage successor bytes on the same filesystem, flush data and metadata using the platform's strongest applicable durability primitives, atomically replace the target where supported, and hold process-wide OS custody across preflight, SQL claim, file operation and readback. Windows replacement and SQLite commit are **not** one atomic durable transaction.

## Protected transaction and one-write sequence

`ProtectedLocalReceiptDispatcher` shares the same service-owned SQLite connection as the full chain, creates `plan_local_receipt_dispatch_v1`, and provides `dispatch_once()` and read-only `observe()`. The durable status is `LOCAL_RECEIPT_DISPATCH_CLAIMED_WRITE_OUTCOME_UNCERTAIN`. The service performs exactly these ordered steps:

1. Parse and compare the canonical witness request and all caller-presented reservation, preclaim, protected-receipt, deployment-intent and prewrite-marker data. Require authorized `dispatch_local_receipt_once`, a provisioned reader, a real service-owned file writer and pinned signed-witness material.
2. Enter `BEGIN IMMEDIATE`; independently reread the **actual persisted** reservation, preclaim, protected receipt, deployment intent and prewrite marker on the *same* service connection. Reject missing or changed records, even if a supplied Python object claims success. Refuse an existing dispatch claim, including byte-identical replay.
3. Require fresh independent stopped-writer, package and consent evidence, a safe protected local readback matching the **exact predecessor**, stable recovery capsule and pending journal/selection, and a new pinned-key signed witness readback confirming the exact successor revision/generation/digest.
4. Insert the once-per-installation immutable dispatch claim and `COMMIT`. **The claim must become durable before any filesystem write callback is invoked.** An uncertain SQLite acknowledgment requires read-only inspection, never a blind retry.
5. Invoke the independently provisioned `service_owned_write` **once**, outside the committed SQLite transaction and within an externally held OS-level exclusive critical section. There is no rollback, compensation, automatic rearm, overwrite retry or capsule mutation operation. A raised exception or lost ACK leaves `WRITE_OUTCOME_UNCERTAIN`.
6. Independently reread the local receipt, pending recovery state, installed bytes and signed witness, and accept only exact successor bytes plus unchanged protected preimages. Return `LOCAL_SUCCESSOR_VISIBLE_CAPSULE_RETAINED_RECOVERY_REQUIRED`. Even successful readback does **not** clear the capsule, transition journal, change selection or enable launch.

The durable claim intentionally does **not** transition to `SUCCESS`, even after successful local readback. A callback may finish after its coordinator loses an ACK; an apparent predecessor file may coexist with a still-running write. Subsequent reconciliation must explicitly fence pending writers before reasoning about terminal state. **Do not redispatch.** The record is one-way and has no reset, DELETE, UPDATE or second-attempt API.

## Security and crash obligations

Tests use an in-memory/synthetic service, synthetic signed witness, and a filesystem callback that writes temporary test files. They exercise sequencing and negative behavior, but do **not** validate real Windows ACLs, safe handle-based replacement, post-power-loss directory metadata, reparse points, impersonation, service key custody or persistent installation-wide locking. A true privileged writer implementation and crash/fault-injection acceptance should be reviewed independently before production deployment.

This slice does not clear `pending-slot-recovery.json`, publish launcher readiness, change module selection, retry a failed write, roll back software, perform CAS, or claim teacher-local trusted state. **Next** is durable independent convergence/reconciliation after dispatch with explicit OS-level writer quiescence and controlled recovery disposition, preserving the capsule until all requirements are met.
