```text

```


## Preliminary findings

### RA-001 — Core artifact execution preceded exact authentication

**Classification:** release blocker
**Owner:** suite CI/release infrastructure
**Disposition:** corrected in issue #14 slice 1

At the audit baseline, the ordinary cross-platform `validate` job downloaded
the official Core v0.6.3 wheel and installed it before independently checking
the wheel bytes against the exact SHA-256 in the suite compatibility manifest.

The dedicated release-artifact and combined-suite jobs authenticated component
artifacts, but release-critical validation still executed one PDS-owned wheel
before exact authentication.

The corrected trust order is:

```text
download exact declared Core wheel
-> read exact Core release identity from bundled manifest
-> verify filename
-> calculate SHA-256
-> require exact manifest digest
-> only then install Core
```

The later full compatibility-artifact verifier continues to provide the
stronger wheel metadata and entry-point cross-check.

## Architecture/source audit progress

Initial source review found no production imports of Quillan, ScoreForm,
Concord, or Vitrine implementation modules. The suite continues to use public
installed-distribution/entry-point boundaries rather than sibling-private menu
imports.

Backup creation was reviewed for the primary stable-path safety contract. The
implementation:

- obtains the canonical workspace from Core;
- inventories without following symbolic links;
- refuses redirecting Windows symlink/mount-point reparse entries;
- rejects non-portable manifest paths;
- performs semantic source/destination containment checks;
- re-resolves the destination after confirmation;
- rechecks source inventory and hashes;
- independently verifies staged bytes before publication; and
- documents that it is not an adversarial operating-system snapshot/locking
  mechanism.

No stable-path traversal or semantic-ownership release blocker was identified in
that initial pass. Adversarial same-user filesystem mutation remains a documented
threat-model limitation and continues to be audited rather than silently claimed
away.

## Additional read-only audit findings

### RA-005 — Package Python metadata is deliberately broader than suite qualification

**Classification:** deliberately out of scope / intentional compatibility boundary
**Owner:** suite compatibility architecture
**Disposition:** accepted as designed

The package metadata declares:

```text
Requires-Python: >=3.11
```

while the exact release manifest qualifies:

```text
>=3.11,<3.15
tested: 3.11, 3.12, 3.13, 3.14
```

The release-compatibility architecture explicitly documents this distinction.
Package-installer acceptance is not suite qualification. A future Python 3.15
interpreter may satisfy package metadata but must remain unqualified until a
later suite release explicitly tests and admits it.

No package-metadata narrowing is required for v0.1.0.

### RA-006 — Suite-settings higher ancestry is an OS/user configuration boundary

**Classification:** deliberately out of scope / low-risk path-model observation
**Owner:** suite settings + operating-system user configuration
**Disposition:** accepted; no runtime change

The suite settings implementation rejects symbolic-link/reparse redirection at
the application-owned settings directory and at the settings file itself, uses
same-directory temporary files, and atomically replaces the complete validated
document.

Higher ancestry can reflect a user-configured or symlinked home/config root.
The CLI does not accept an arbitrary settings-file path, and settings schema v1
stores only bounded top-level component IDs, not workspace/student/domain state.
Rejecting all higher redirected ancestry would unnecessarily reject legitimate
OS/user configuration without materially protecting classroom data.

The audit therefore keeps the existing boundary rather than broadening path
rejection beyond the application-owned settings directory.

### RA-008 — Restore stable-path/non-overwrite contract review

**Classification:** audit pass
**Owner:** suite opaque-custody restore
**Disposition:** no blocker found

The restore implementation was reviewed against the v1 contract. It:

- independently verifies the backup before planning;
- requires an explicit destination that does not already exist;
- rejects overlap with the backup/payload/current Core workspace;
- re-verifies the backup and Core workspace immediately before mutation;
- re-resolves destination ancestry after confirmation;
- stages bytes separately;
- hashes copied bytes against the reviewed manifest;
- independently verifies staged inventory and SHA-256 values;
- publishes through a no-replace directory rename primitive; and
- never merges, overwrites, semantically rewrites, or automatically selects the
  restored workspace.

No stable-path overwrite/merge release blocker was identified.

### RA-011 — Backup publication no-replace race hardened

**Classification:** release blocker / required release hardening
**Owner:** suite workspace-backup orchestration
**Disposition:** PASS after issue #14 slices 5–5b and focused regression gate

The backup implementation already provided strong source/destination protections:
read-only preview, workspace re-resolution, source inventory drift detection,
link/reparse/special-entry rejection, free-space recheck, exclusive staging,
streamed hashes, source re-hash after copy, independent staged-payload
verification, canonical manifest read-after-write validation, and staging
cleanup.

The final publication step nevertheless used a check-then-`os.rename` sequence.
On POSIX, `rename` may replace an existing empty destination directory. A
destination created in the interval between the existence check and rename could
therefore be replaced, violating the release requirement that backup publication
never overwrite/collide silently.

Slice 5 aligns backup publication with the already-qualified restore strategy:

- Windows uses native rename behavior, which refuses an existing destination;
- Linux uses `renameat2(..., RENAME_NOREPLACE)` when available;
- macOS uses `renamex_np(..., RENAME_EXCL)` when available;
- unsupported POSIX environments fail closed rather than fall back to replacing
  `rename` semantics;
- collision errors preserve the pre-existing destination and owned staging is
  cleaned through the existing failure path.

The independent backup-verification implementation was also re-audited and no
additional release blocker was found.

### RA-012 — Shared classroom setup safety and usability audit passed

**Classification:** usability / privacy / ownership audit
**Owner:** suite shared-classroom orchestration
**Disposition:** PASS with documented non-blocking limitation

The guided `pds setup` workflow was re-audited across assessment, planning,
terminal review, APPLY preflight, execution, failure reporting, documentation,
and tests.

Release-critical properties are satisfied:

- assessment and planning use only exact-qualified public Core readers,
  validators, factories, guarded roster planners, and starter-pack merge services;
- writer services are not loaded until the teacher types exact uppercase `APPLY`;
- the final review shows bounded class/roster counts and standards/framework
  merge facts without dumping roster rows, names, student IDs, or the selected
  roster source path;
- before the first mutation, Core shared state is fully re-assessed and compared
  with the reviewed assessment;
- guarded roster current/candidate state tokens are revalidated before APPLY and
  supplied unchanged to Core's guarded commit;
- the selected standards pack is dry-merged again before mutation and receives
  an additional just-in-time baseline recheck before installation;
- standards definitions, profiles, and framework metadata are compared together;
- Academic Period current state/revision is rechecked before mutation;
- existing conflicting state is refused rather than overwritten;
- post-write verification re-reads the relevant Core state;
- later failure after earlier writes is reported as partial success with no false
  rollback claim and explicit safe-rerun guidance.

One starter standards pack is intentionally selectable per `pds setup`
invocation. Qualified additional compatible packs require another explicit safe
rerun. This is a teacher-workload limitation but not a v0.1.0 release blocker:
the workflow documents the limitation, performs no implicit selection, and
already treats matching prior state as `KEEP`. Multi-pack transactional setup
remains deliberately outside the approved v0.1.0 scope.

### RA-013 — First-run, Core-only, and partial-install behavior passed

**Classification:** usability / compatibility audit
**Owner:** suite diagnostics and application inventory
**Disposition:** PASS

The suite distinguishes a usable Core-backed shell from optional application
availability instead of treating every missing optional module as a broken
installation.

Verified behavior:

- missing required Core is a blocking doctor `FAIL`;
- a missing optional qualified application is a doctor `SKIP`, not a false
  failure;
- a Core-only environment can still use Core-backed suite workflows;
- `pds modules` reports absent optional applications as `not installed` with
  bounded bootstrap guidance;
- an installed optional application at the wrong version is `INCOMPATIBLE` /

- one application's entry-point failure is isolated from other applications;
- unrelated installed distributions and PATH-name similarity do not create PDS
  applications;
- launch is refused unless the exact manifest component, distribution version,
  entry-point owner/target, qualified Core, qualified suite, and resolved
  environment-local launcher all agree;
- first-run absence of a configured/initialized workspace remains a truthful
  setup precondition with remediation, not workspace corruption.

### RA-019 — Dependency license and attribution review passed

**Classification:** release licensing / attribution audit
**Owner:** suite packaging and release engineering
**Disposition:** PASS

The suite distribution is MIT-licensed and the built-wheel validator requires
exact MIT license metadata plus packaged repository LICENSE bytes.

The installed PDS composition is deliberately multi-distribution. `pds-core`,
the optional PDS applications, qualified pip tooling, and their transitive
dependencies are installed as separate upstream distributions; they are not
vendored, copied, or relicensed inside the `paper-data-suite` wheel. Their own
license metadata and bundled notice files therefore remain authoritative. The
audit reviewed the resolved dependency composition and upstream license/notice
surfaces, including binary packages that carry their own third-party notices.

No suite-specific `THIRD_PARTY_NOTICES` file was identified as required merely
because bootstrap installs those separate distributions. The release must not
strip or replace dependency license/notice files, and the suite MIT license must
not be represented as covering those dependencies. This is a release-engineering
attribution conclusion rather than institutional legal advice.
