# Paper Data Suite v0.1.0

> **Audit-approved release notes.** The source tree carries the final
> `0.1.0` / `release` identity and the v0.1.0 audit disposition is
> `APPROVE WITH DOCUMENTED NON-BLOCKING LIMITATIONS`. Publication is an
> explicit maintainer action and must use release artifacts built and validated
> from the final tagged source tree.

Paper Data Suite v0.1.0 is the first integrated suite-shell teacher-pilot
release. It provides local-first orchestration around an exact-qualified PDS
composition without taking ownership of Core- or module-owned classroom records.

## Qualified composition

The promoted v0.1.0 identity qualifies:

- Python 3.11, 3.12, 3.13, and 3.14;
- PDS Core 0.6.3;
- Concord 0.2.0;
- Quillan 0.9.0;
- ScoreForm 0.10.0;
- Vitrine 0.2.0; and
- release bootstrap tooling `pip 26.2.1`.

Meridian and Portia are not part of the v0.1.0 qualified application
composition.

Every qualified PDS component is bound to one exact published wheel identity and
SHA-256. Release bootstrap tooling is independently bound to its own exact
authenticated wheel contract.

## Teacher-facing suite workflows

v0.1.0 includes:

- `pds doctor` for read-only environment/workspace/Core/provider diagnostics;
- `pds modules` for exact-qualified application inventory;
- `pds launch <component-id>` for verified out-of-process application launch;
- `pds workspace` for Core-backed workspace inspection, setup, validation,
  selection, and reset;
- `pds setup` for review-before-write shared classroom setup;
- `pds backup create` for verified whole-workspace byte custody;
- `pds backup verify` for independent backup integrity verification;
- `pds backup restore` for non-overwriting alternate-location restoration; and
- `pds settings` for bounded privacy-minimized shell convenience state.

The suite remains an orchestration layer. It does not become an alternate writer
for Core- or module-owned records.

## Platform qualification

v0.1.0 is a **Windows-first teacher pilot**.

The automated suite CI matrix exercises Windows and Ubuntu on Python 3.11–3.14.
Linux CI is software-compatibility evidence; it is not equivalent to the real
teacher-pilot hardware/workflow qualification performed on Windows.

macOS is not release-qualified for v0.1.0.

CI discovery of `pdftoppm`/Poppler proves command discovery only. It does not
prove real printer, scanner, camera, or PDF-imaging hardware operation.

## Security, privacy, and integrity

The release audit includes:

- exact component and release-tool artifact authentication before trusted use;
- pinned GitHub Actions identities;
- managed-runtime dependency vulnerability auditing;
- repository-history and candidate-source secret scanning;
- privacy-bounded diagnostics and setup output;
- opaque backup byte custody without semantic record parsing;
- non-overwriting backup and restore publication;
- explicit backup integrity/authenticity/confidentiality distinctions; and
- release-package content and MIT license verification.

Whole-workspace backups are **not encrypted**, are **not digital signatures**,
and are **not automatically uploaded or cloud-synchronized**. SHA-256 integrity
evidence does not prove confidentiality or authorship.

## Licensing and third-party distributions

The `paper-data-suite` distribution itself is MIT-licensed and packages its
repository LICENSE. That license applies to suite-owned code; it does not
relicense PDS components or third-party Python distributions installed beside
the suite.

Core, optional PDS applications, release tooling, and transitive dependencies
remain separate distributions under their own license metadata and bundled
notices. The suite bootstrap installs authenticated upstream wheels rather than
vendoring or repackaging those projects into the suite wheel, and it must not
strip their license/notice files. Binary dependency wheels that carry upstream
third-party notices retain those notices in their own installed distributions.

The v0.1.0 dependency-license review found no suite-specific notice file required
for separately distributed dependencies. This is a release-engineering
attribution conclusion, not a substitute for institutional legal review.

## Known non-blocking limitations

- Guided `pds setup` selects one Core starter standards pack per invocation.
  Additional compatible packs require another explicit safe rerun.
- The qualified v0.1.0 application composition does not declare a shared
  `paper_data_suite.module_operations` readiness provider, so that doctor
  category truthfully reports `SKIP`.
- macOS is not release-qualified.
- Real printer/scanner/imaging operation is outside automated CI evidence.
- Persistent diagnostics, troubleshooting bundles, dashboards, mixed paper
  intake, group-planning interoperability, cloud backup/sync, and multi-user
  authorization remain outside v0.1.0 scope.

## Support

v0.1.x is an early pilot series. Once releases exist, only the latest released
`0.1.x` version is supported; `main` is development-only. There is no LTS,
guaranteed backport window, or vulnerability-response SLA.

Sensitive vulnerability reports must use GitHub Private Vulnerability
Reporting, which was maintainer-confirmed enabled before promotion.
